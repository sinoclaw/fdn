# 自研计算原语：探针验证方案（判据先行 + 诚实边界）

> **作者**：陈亦安（安安）
> **背景**：爸爸认可"把 DCA 的独立路径+稀疏门控下沉成真正的 token 计算原语"。但 BDH（伪稀疏可导→CPU稠密不降本）与 FDN/MoE（真稀疏不可导→学不会）已在 CPU 上双双撞墙。本探针**最小成本回答**：能否在 CPU 上造出"既真稀疏又可导"的计算原语。

---

## 1. 两难（已用 BDH/FDN 实测钉死）

| 候选 | 稀疏类型 | 可导 | CPU 结果 |
|---|---|---|---|
| BDH（超大N+ReLU）| 伪稀疏(全通道) | 可导 | 稠密GEMM → 贵5倍 |
| MoE/FDN（top-k）| 真稀疏(少量通道) | 不可导 | 学不会（梯度断）|

**研究问题**：是否存在一个 token 计算层，**只激活少量通道（真稀疏）**且 **所有激活通道都能拿到梯度（可导）**，从而 CPU 上既降本又可学？

## 2. 候选原语：FastWeights 独立路径 + 软稀疏门控

借鉴 DCA 已验证的 FastWeights v3（每能力独立路径，稀疏但独立门控），构造单层原语：

```
x (B,T,D)
  → 每 token 计算 keys (k), queries (q) 到 N 个"快速权重槽"
  → 通过连续软化（top-2 加权，Gumbel-softmax）选少量槽 —— 真稀疏但可导
  → 被选的槽用 Hebbian 式更新 fast weight（状态在边权）
  → 该 token 的输出 = 所选槽的 fast weight 作用于 q
```

**关键差异 vs BDH/FDN：**
- vs BDH：用**真稀疏**（每 token 只算~2 个槽，不是全 N 通道 relu）→ 避免稠密 GEMM
- vs FDN/MoE：用**连续软化**（Gumbel-softmax / top-2 加权）→ 避开离散 top-k 的梯度断

## 3. 判据（判据先行，跑前锁死）

### 探针判据（最小可行性）：
- **P1 可训**：loss 能下降（非随机），证明"真稀疏又可导"的模型能学。
- **P2 真稀疏**：统计平均每 token 激活的槽数 << N（证实不是稠密）。
- **P3 降本（对比 Transformer 单层）**：同参数规模、同预算下，
  - 训练 wall-clock ≤ Transformer 单层
  - 推理 wall-clock ≤ Transformer 单层

### 判定：
- **P1+P2+P3 全成立** → 自研计算原语在 CPU 上**走通**（真稀疏又可导且降本），值得全面展开。
- **P3 失败（能学、真稀疏但不降本或更贵）** → 如实记录"CPU 上稀疏激活的降本红利仍需 GPU 稀疏内核兑现"，同 BDH 结论，CPU 环境验证不了降本。
- **P1 失败（学不会）** → 记录"软稀疏原语难训"，同 MoE 结论。
- **无论结果，如实交付，不硬凑。**

## 4. 实验设计（一次只动一组变量）

1. 在字符级语言建模上，实现上述 FastWeights+软稀疏门控单层原语。
2. 对照 = 单层 Transformer（等参数规模）。
3. 固定：数据集、block size、batch、iters、lr、seed、参数规模目标。
4. 测 P1（loss 曲线）、P2（激活槽数统计）、P3（训练/推理 wall-clock）。
5. ≥3 seed 取均值。

## 5. 诚实边界（事前锚定）
- 本探针只回答"CPU 上能否造出可导真稀疏+降本原语"，**不回答** GPU 上大模型的落点。
- 若 P3 失败，结论是"CPU 环境是瓶颈，需 GPU 稀疏内核"——这与 BDH 失败一致，是**环境约束**而非"机制一定不行"。
- 不预设结论，用真实数据说话。
